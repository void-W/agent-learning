# 适配器消息映射效果实验

- 证据范围：[DSH 实现](../implementations/DSH工作区指令到模型请求.md) 支持结构差异分析，不支持效果差异结论

## 问题与假设

问题来自本次学习讨论：统一 Session 历史映射到模型请求时，适配策略是否影响效果？背景见 [API adapter 与输入语义](../concepts/API适配器与模型输入语义.md)。本页是对讨论的整理，不是完整对话记录或实验结果。

**待验证假设 H1**：同一 API、同一模型接受的不同合法消息边界表达，可能影响工具结果理解或规则遵循；差异也可能无法测出。

**待验证假设 H2**：把结构化工具结果降级为普通文本，可能改变结果关联和来源区分。但这不是仅改变消息边界，必须作为单独、有损策略实验，不能与 H1 混淆。

## 先确认协议允许，再比较

1. 选择具体 API 和模型，查官方文档并验证候选请求合法。
2. 只有协议允许合并与分离两种等价内容表达时，才测试消息边界。若一方不合法，记录能力限制，不把 API 拒绝当作模型质量差异。
3. 结构化工具结果与纯文本降级的比较单独进行；不能假定目标 API 同时支持独立 tool 角色和 user 内工具结果块。
4. 用相同规范化输入生成并审阅两种最终请求，记录全部不同字段，避免隐藏变量。

## 候选最小任务

| 场景 | 要检验的行为 | 指标候选 |
| --- | --- | --- |
| 工具返回两个不同值 | 正确使用指定调用的结果 | 答案准确率、结果错配次数 |
| 工具成功与错误混合 | 识别错误而非编造成功 | 错误识别率、错误处理表现 |
| 工具结果后追加新 scope 规则 | 使用新增工作区约定 | 明确约定的遵循率 |
| 已加载规则后追加更新通知 | 不继续依赖旧规则 | 更新遵循率、冲突回答数 |

这些指标只覆盖设计的任务，不构成通用能力或安全评估。打分规则需在收集结果前明确。

## 控制与记录

- 固定模型、API、system／developer／用户正文、工具 schema、工具结果、内容顺序、采样与 token 配置。
- 记录 provider、模型 ID、API 路由、SDK／adapter commit、策略名、请求时间和服务版本（可得时）。
- 对变化的表达记录最终请求体与差异；凭据永不归档，任务使用合成无敏感数据。
- 随机或交错请求顺序，多任务、多次重复，报告样本数和不确定性；同一 seed 或温度为零也不当作完全可重复保证。
- 可得时记录延迟、使用量和缓存数据。未提供的指标标为未知，不从体感推断。

## 结构验证与效果验证分开

请求快照用于检查角色、工具 ID、内容顺序、合并和降级；模型评测用于检查任务表现。先做结构测试，再开展 API 实验；不得用“快照通过”声称效果更好。
