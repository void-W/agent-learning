# 思考强度切换缓存实验

- 类型：受控实验记录
- 创建／更新：2026-11-08（Asia/Shanghai）
- 状态：已完成一次受控运行；结果支持 H3；待跨模型／端点复现
- 证据范围：[DeepSeek-V4.1-Flash 对话模板](../sources/DeepSeek-V4.1-Flash对话模板.md)、[DSH 实现](../sources/DSH源码阅读基线.md) 与 2026-11-08 官方 Messages API 实测

## 问题与假设

会话中途切换思考强度后，提供方缓存还能命中吗？公开模板显示强度被写成模型输入开头的一段文本，因此推断前缀会从很靠前的位置失效；但托管 API 是否逐字使用该模板，需要实测。背景见 [API 适配器与模型输入语义](../concepts/API适配器与模型输入语义.md)。

**待验证假设 H3**：同一会话中只切换思考强度、其他输入不变时，切换后的首次请求缓存命中率接近 0，而不是只损失末尾少量 token。

**竞争解释**：如果命中率仍然很高，说明托管 API 没有把 effort 写进前缀，或缓存键与服务端 prompt 构造和公开模板不同。

## 方法

使用 [思考强度缓存验证脚本](../../experiments/思考强度缓存验证/verify_effort_cache.py) 直接请求官方 Messages API：

- 端点：`https://api.deepseek.com/anthropic/v1/messages`；
- 模型：`deepseek-flash`；
- system prompt 12,000 字符，user message 固定为 `Reply with exactly OK and nothing else.`；
- 每次请求的 system 与 user 完全相同，只改变 `thinking`／`output_config.effort`；
- 序列：`high → high → low → low → high`，间隔 5 秒；
- 读取 `usage.input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`、`output_tokens`。

密钥通过工作区根目录 `.env` 提供，脚本自动查找；结果 JSON 不保存密钥。

## 实测结果

运行时间：2026-11-08 01:14（Asia/Shanghai）。原始记录：[effort-cache-20261108-011514.json](../../experiments/思考强度缓存验证/results/effort-cache-20261108-011514.json)。

| # | effort | 角色 | input | cache_read | cache_create | output | total_in | 命中率 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | high | 暖场 | 1989 | 0 | 0 | 2 | 1989 | 0.00% | 冷启动 |
| 1 | high | 同 effort 对照 | 197 | 1792 | 0 | 11 | 1989 | 90.10% | 前缀命中 |
| 2 | low | 只切 effort | 1989 | 0 | 0 | 2 | 1989 | 0.00% | 切换后冷启动 |
| 3 | low | low 稳定态 | 197 | 1792 | 0 | 2 | 1989 | 90.10% | low 自己的前缀命中 |
| 4 | high | 回切 | 197 | 1792 | 0 | 2 | 1989 | 90.10% | 回到此前 high 的前缀 |

每次请求总输入均为 1989 tokens；命中时 1792 tokens 来自缓存，197 tokens 未缓存。本实验没有进一步定位这 197 个 token 的具体位置。

## 解释

**支持 H3（本次运行）**：`high → low` 的首次请求命中率从 90.10% 降到 0.00%，说明仅改变 effort 就足以让整个前缀无法完整匹配；这不是“只损失末尾少量 token”的表现。

同 effort 对照 `high → high` 命中 90.10%，说明固定输入下缓存正常工作，排除了“缓存完全不可用”的解释。

`low → low` 再次命中 90.10%，说明 low 也建立了自己的前缀缓存。

`low → high` 回切仍命中 90.10%，说明 low 请求没有清空此前 high 的前缀缓存；不同 effort 的缓存前缀可以并存，切换回旧 effort 能复用旧前缀。这与“缓存以完整前缀单元匹配”一致。

## 判定

- **支持 H3**：切换后首步命中率接近 0，且输入规模与切换前相近；本次满足。
- **不支持 H3**：切换后命中率仍高，或只有末尾少量未命中；本次不成立。
- **部分支持**：命中 tokens 明显下降但未归零；本次不适用。

本次结果只覆盖 `deepseek-flash`、官方 Messages 端点、12,000 字符前缀、单次运行。它不能自动推广到其他模型、其他提供方、其他 API 协议或更短上下文；缓存仍是 best-effort，缓存构建、淘汰和请求间隔都会影响结果。

## 复现

在工作区根目录 `.env` 填写 `DEEPSEEK_API_KEY`（模板为 `.env.example`）；脚本会向上查找最近的 `.env`，也可用 `--env-file` 指定。

```sh
cd experiments/思考强度缓存验证
python3 verify_effort_cache.py --dry-run
python3 verify_effort_cache.py --model deepseek-flash --sequence high,high,low,low,high --delay 5
```

脚本输出终端表格并在 `results/` 写入 JSON。真实请求会计费；先干跑确认。不要把密钥写入结果或提交。

## 手动备选与 DSH 统计页

1. **记录基线**：在切换前完成一次正常请求，记录当前 provider／模型、思考强度，以及该步的缓存命中 tokens、未命中 tokens（或命中率）。
2. **只切强度**：通过 `/model` 或 composer 切换思考强度（例如 `high` → `low`），不要同时改模型、system prompt、工具或工作区。切换从下一个 step 生效。
3. **立即发一条短消息**：触发切换后的第一个请求；记录该步和该轮的缓存命中数据。不要先做文件编辑或工具调用，避免引入其他前缀变化。
4. **可选回切**：再从 `low` 切回 `high`，重复一次，形成 A→B→A 两个数据点。

- **“统计”页签**：每轮一行，展开后列出各步的缓存命中率；悬停可看汇总的缓存读／输入／写明细。见 [client-ui-stats README](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/experimental/client-ui-stats/README.zh.md#L12)。
- **输入框用量控件**：显示 token 总量与缓存命中；详细模式提供会话统计和每轮 token 用量。见 [ui-chat README](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/client/ui-chat/README.zh.md#L79-L81)。

## 混淆因素

- 切换与请求之间间隔过久，缓存可能已被淘汰；尽量立即发起下一次请求。
- 上下文太短，命中率的统计噪声大；本次使用约 2,000 tokens 的固定前缀。
- 同时改变 prompt、工具、图片或模型，会从其他位置打断前缀，无法归因于 effort。
- 只比较百分比而不看 tokens，可能被不同步骤的输入规模误导。
- 同一请求重试、压缩、上下文刷新或工具结果追加，都可能改变前缀。

## 当前结论与下一步

本次受控运行支持“思考强度被编码进模型输入开头，切换 effort 会使缓存前缀失效”的判断；同时表明不同 effort 的前缀缓存可以并存，回切旧 effort 仍能命中。

下一步优先用同一脚本测试 `deepseek-v4-pro` 或不同前缀长度，确认结论的适用范围；如果结果一致，再把概念页的“单次实测”提升为更一般的表述。不要用一次运行推断所有提供方的缓存行为。
