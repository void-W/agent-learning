# 工作区指令与上下文注入

- 类型：概念
- 创建／更新：2026-11-07（Asia/Shanghai）
- 证据范围：[DSH 固定版本源码与文档](../sources/DSH源码阅读基线.md)；不概括所有 Harness 的实现

## 需要区分的对象

| 对象 | 含义 |
| --- | --- |
| 规则文件 | 工作区中的维护约定，例如 `AGENTS.md` |
| 发现策略 | 何时、沿哪些目录、以什么预算读取规则 |
| 内部消息 | Harness 用 role、content、source 等信息表示上下文 |
| 持久事件 | 记录哪些消息在什么位置进入会话历史 |
| 模型请求 | 从有效历史派生，再转换为具体 API 接受的格式 |

**推断**：支持规则文件不只是读取 Markdown；完整设计还需定义作用范围、发现时机、更新与移除、持久记录、预算和信任策略。DSH 提供一个可研究的实例，不是唯一实现方式。

## DSH 实例说明什么

**实现事实**：DSH 的指令插件把规则包装成带来源的 user 消息，而非动态改写 system prompt。`<system-reminder>` 是文本框架，不是 API 的 system 角色。具体源码和完整流程见 [实现分析](../implementations/DSH工作区指令到模型请求.md)。

**实现事实**：规则的添加、更新和移除以新上下文消息追加到历史。“替换规则”在此表示通知模型旧规则已改变，不意味着删除之前的对话事件。未改变内容受到版本／digest 对账抑制，避免重复注入。引用与限制见 [实现分析的更新语义](../implementations/DSH工作区指令到模型请求.md#更新与移除)。

**推断**：持久上下文让维护者能够追踪模型当时看到了哪些规则；追加而不重写既有消息有利于保留请求前缀。但这不保证模型一定服从最新规则，也不保证服务端实际命中缓存。

## 信任与角色

**设计建议**：框架的高优先级规则、用户当前请求、仓库约定和工具返回应保留来源区别。规则文件包含自然语言，不应因文件名或 XML 风格标签被自动提升到系统权限。

**限制**：提示词中的“不得覆盖 system／developer／用户指令”是模型可见约定，不等于文件系统访问控制或不可绕过的安全策略。需要权限约束时，应由操作执行层落实。当前没有针对本实例做安全实验。

## Go 框架可探索的设计

以下仅是候选方案，尚未在 [Go 目标仓库](https://github.com/void-W/plugin-harness-go) 实现或确定：

- 文件发现、规则渲染和消息派生各有明确职责；规则插件通过上下文入口贡献消息，不直接改 LLM 请求。
- 规则消息带来源、scope 和变更记录；在确定的步骤边界进入持久历史。
- 未改变的规则不重复加入；新发现、替换和移除应可测试。
- 预算覆盖实际发送的完整文本；失败与降级应可观测。

最终线上表达还取决于 [API adapter](API适配器与模型输入语义.md)，不能从内部消息结构直接推断模型收到的完整请求。
