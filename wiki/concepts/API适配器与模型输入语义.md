# API 适配器与模型输入语义

- 类型：概念与设计分析
- 创建／更新：2026-11-08（Asia/Shanghai）
- 证据范围：[DSH 固定版本](../sources/DSH源码阅读基线.md) 的局部实现、[DeepSeek-V4.1-Flash 对话模板](../sources/DeepSeek-V4.1-Flash对话模板.md)，以及 2026-11-08 在 `deepseek-flash` 官方 Messages API 上的一次受控运行

## 核心认识

**推断**：API adapter 不仅转换字段，也决定统一历史如何在目标协议中表达。统一 Session 建模使系统内部事实可记录、可追溯，但不保证不同适配器生成同样的线上输入，或得到等价的模型行为。

```text
Session events
  → 当前有效历史及消息投影
  → 内部 messages
  → API 请求体
  → 提供方 chat template
  → 模型 token 输入
  → 输出
```

以上是分析框架。本次已检查 DSH 的 API 请求构造和 DeepSeek 的公开模板，并测量了一组托管 API 的缓存命中；仍未抓取服务端最终 token 序列。

## 已核实的具体实例

**实现事实**：当前 DSH DeepSeek Messages adapter 把内部工具结果表示为 user 消息内的 `tool_result`，并合并相邻同角色消息。它构造 API 所需字段，不原样发送内部的消息 `id` 与 `source`。详见 [DSH 序列化分析](../implementations/DSH工作区指令到模型请求.md#deepseek-api-序列化)。

结构化 `tool_result` 即使位于 user 消息内，也仍有工具调用关联；它不等于普通用户文本。不能仅凭外层角色判断权威性，更不能推断一定比独立 tool 角色效果差。

## 模板层证据：思考强度会改写开头

**来源事实**：DeepSeek-V4.1-Flash 的公开 chat template 在消息序列第一个元素处，先输出 `<｜System｜>`，再在 thinking 模式下输出一段普通文本：

```text
Reasoning Effort: 75 (range 1-100, the higher the value, the more thorough the reasoning)
```

随后才输出 system 正文。字符串强度映射为 `low=50`、`medium=62`、`high=75`、`max=100`。见 [模板来源页](../sources/DeepSeek-V4.1-Flash对话模板.md)。

**推断**：切换思考强度不是只改一个请求参数；它改变了模型输入开头的文本。按 DeepSeek 文档的完整前缀单元匹配规则，第一个不同 token 之后的缓存单元不能完整匹配。切换 `low`／`high`／`max` 之间时，thinking 都开启，历史 reasoning 保留，但开头数字变化；切 `off` 时整行消失，并可能改变历史 reasoning 的渲染。缓存影响接近一次冷启动，而不是末尾少量未命中。

**实测结果（2026-11-08，`deepseek-flash` 官方 Messages API）**：固定 12,000 字符前缀，仅切换 effort。`high → high` 命中 90.10%（1792/1989）；`high → low` 命中 0.00%；`low → low` 命中 90.10%；`low → high` 回切仍命中 90.10%。这支持“effort 进入前缀”，也说明不同 effort 的前缀缓存可以并存，回切旧 effort 能复用旧前缀。详见 [实验记录](../explorations/思考强度切换缓存实验.md)。

**限制**：这是开放权重模型的公开模板，不是托管 API 的逐字保证。上述实测只覆盖 `deepseek-flash` 官方 Messages 端点、约 2,000 tokens 前缀和单次运行；其他模型、端点、协议或更短上下文仍需验证。缓存仍是 best-effort。

## 哪些差异值得检查

下面是一般性的适配检查维度，不表示 DSH 已提供这些可切换策略，也不表示所有 API 都支持两种表达。

| 维度 | 要问的问题 | 可能影响 |
| --- | --- | --- |
| 角色和消息边界 | 指令是否改变角色，相邻消息是否合并？ | 来源表达、模板、缓存 |
| 工具调用与结果 | ID、顺序、错误标记是否保留？ | 协议合法性、结果关联 |
| 历史 reasoning | API 要求什么，如何保留或降级？ | 信息连续性、请求合法性、成本 |
| 内容处理 | 空内容、超长内容、附件如何表达？ | 信息损失和 token 消耗 |
| 参数与 schema | 参数是否重编码，工具定义如何转换？ | 表示变化与工具调用表现 |
| 不支持能力 | 报错、显式降级还是静默省略？ | 可观测性与功能保证 |

**证据状态**：公开模板和 2026-11-08 的受控运行都支持“effort 进入缓存前缀”；在 `deepseek-flash` 官方 Messages API 上，切换 effort 使命中率从 90.10% 降到 0.00%。这仍是一次单模型、单端点的结果，不能自动推广到所有提供方。其他映射对回答质量、工具调用成功率或延迟的影响也仍需实验，不能由结构差异直接推断。

## 不要把适配差异全部归因于模型

```text
模型 A + 适配路径 A  vs.  模型 B + 适配路径 B
```

**推断**：此比较同时改变模型和输入表达，不能单独证明模型能力差异。即使模型相同，也应记录请求配置、工具定义、适配策略和服务端可知版本。

**限制**：最终请求体一致也不保证单次输出一致；采样、服务版本变化和其他服务端因素仍可能影响结果。请求快照用于检查映射，不代替行为评测。

## 给 Go 框架的候选要求

**设计建议，尚未实现或最终采纳**：

1. 定义必须保留的语义：调用结果关联、文本顺序、指令来源、错误状态。
2. 声明 provider 能力与不支持时的处理方式，重要信息不能悄悄丢失。
3. 对事件到消息、消息到最终请求分别测试；记录提供方模板是否把配置写进 prompt 前缀，避免只检查内部对象。
4. 保留 adapter 版本、策略和请求配置；若需归档实际请求，先处理敏感数据。
5. 用请求快照验证结构，用 [控制变量实验](../explorations/适配器消息映射效果实验.md) 验证效果。
